## 1. 왜 만드나

### 문제

지금은 기준 문서 3종(의뢰서·브랜드 가이드·체크리스트)과 납품물(1차 시안·수정본·재수정본)을 사람이 눈으로 대조한다. 관련 역할은 검수 담당자, 제작 담당자, 최종 승인자다.

| 문제 | 내용 |
| --- | --- |
| 조건 누락 | 기준이 흩어져 있어 조건을 빠뜨리기 쉽다 |
| 반복 대조 | 수정본마다 다시 대조하고, 틀린 위치를 따로 설명한다 |
| 버전 혼동 | 예전 결과를 쓰거나 최신본이 아닌 파일을 승인한다 |
| 확인 없는 통과 | 판단할 수 없는 항목이 통과로 처리된다 |

실제 사례: 제67회 백제문화제(2021) 포스터는 영문 회차를 'The 76th'로 적었다. 일정도 공식 일정 9.25(토)~10.3(일)보다 하루씩 밀린 9.26(토)~10.4(일)였다. 2021-09-26은 일요일이라 날짜와 요일이 어긋나므로 달력 검사로 이상을 잡을 수 있다. 하루씩 밀렸다는 것은 공식 일정과 대조해야 확정된다.

### 목적: AI는 초안, 사람은 확정

| 단계 | AI가 맡는 일(초안·근거) | 사람이 맡는 일(확정·승인) |
| --- | --- | --- |
| 조건 | 기준 문서에서 검수 조건 추출 | 추출된 검수 조건 확정 |
| 판정 | 조건별 판정 초안과 근거 제시 | 판정 초안과 근거 검토 |
| 승인 | 승인하지 않는다 | 최종 승인 |

### 기대효과

| 사용자 | 달라지는 점 |
| --- | --- |
| 검수 담당자 | 대조 대신 검토에 집중한다. 조건별 판정 초안에서 시작한다 |
| 제작 담당자 | 고칠 위치와 수정 사유가 담긴 요구서를 받는다 |
| 최종 승인자 | 기준 버전·납품물 버전·검수 결과를 한 묶음으로 보고 승인한다 |

문제 정의와 기대효과는 기획 가설이다. 사용자 인터뷰와 업무 시간 측정은 아직 하지 않았고, 기준선을 잰 뒤 목표치를 정한다.

### 인크로스 연계와 시장

- 인크로스(SK네트웍스 자회사)는 미디어렙·검색광고·광고 기획·제작을 함께 한다. 광고 흐름 '광고주 의뢰 → 소재 제작 → 납품 전 검수 → 매체 심사 → 집행·리포트'에서 이 서비스는 **납품 전 검수** 자리에 들어간다. 매체 심사는 매체사 정책 준수를 보고, 이 서비스는 의뢰 조건과의 일치를 본다.
- 경쟁 서비스(기능 확인 2026.10.06, 가격 2026.10.14 월 결제 기준): Filestage AI Review Agents는 Business 요금제(월 $399)부터, Ziflow ReviewAI는 Enterprise 요금제에서만 제공하며 둘 다 한국어를 지원하지 않는다. Frame.io에는 AI 조건 대조가 없다.
- 1회 검수(재검수 미포함) 원가 추정은 약 250원이다. GPU 서버 1대 상시 가동, 38개사 × 월 100건을 가정했고, 서버 66% · LLM 34%다. 38개사는 유효 시장 3,818개사의 1%로 잡은 첫해 목표(가정)다(기획서 v04 3-1, 발표 숨김 슬라이드).

## 2. 서비스 흐름과 기능 범위

### 5단계 흐름

1. **등록**: 기준 문서와 광고 이미지를 등록한다.
2. **기준 확정**: AI가 추출한 조건을 담당자가 확인·확정한다.
3. **검수**: 확정한 조건 전체를 문구·시각 요소별로 검사한다.
4. **수정 요청**: 근거와 '확인 필요' 항목을 검토하고 수정 요청을 전달한다.
5. **재검수·승인**: 수정본을 전체 재검수한 뒤 최종 승인자가 최신본을 승인한다.

1차 도메인은 행사·축제 포스터, 광고 납품물은 2차 확장이다. 동영상은 5주차부터 다룬다.

흐름은 세 단계다.

1. **기준 준비**: A01 접수 → A02 조건 초안 ↔ A03 근거 검색 → **H1 사람의 기준 확정**
2. **병렬 검수**: 확정 기준 전체를 A04 문구 검수와 A05 시각 요소 검수가 나눠 본다 → A06이 판정·근거·남은 불확실성을 검증한다
3. **결과·조치**: A07 보고서 → A08 수정·재검수 관리 → 사람의 수정 요청·완료 확인 → 수정본은 새 실행으로 A01에 돌아간다. 승인 검토(최신 버전 일치, 필수 미해결 없음)를 통과하면 **H2 사람의 최종 승인** → 기록 → 검수 완료. 통과하지 못하거나 반려되면 E8이다.

### 6.2 posters-v2 실험 (이 저장소, 2026-10-19)

같은 조건에서 세 OCR 경로가 포스터 표준 필드를 얼마나 뽑는지 비교했다.

- **경로**: EasyOCR 1.7.2(main baseline 설정), PaddleOCR 3.7.0(main paddle-only와 같은 모델), 혼합(EasyOCR 줄 중 신뢰도 0.7 미만이거나 핵심 근거인 줄을 최대 8개 골라 Paddle로 다시 읽음, main 규칙 그대로).
- **입력**: `rgb_1x`(원본), `rgb_2x`(LANCZOS 2배). OCR 줄은 같은 규칙 추출기로 표준 문서가 된다. 추출기는 OCR 글자를 고치지 않고 위치·크기·낱말 규칙만 쓴다.
- **장비**: Windows 11 노트북(Intel Core i5-1135G7, RAM 16GB, GPU 없음).

평가 절차(과적합 방지):

| 단계 | 데이터 | 내용 |
| --- | --- | --- |
| 1. 규칙 v1 개발 | dev 60 | test·예비는 열지 않음 |
| 2. v1 고정(`FREEZE`) → 평가 | test 140 | 판독률은 같은데 필드 정확도가 크게 떨어짐 → 과적합 확인 |
| 3. 규칙 v2 개발 | dev + test | 두 분할 각각에서 좋아지는 규칙만 채택 |
| 4. v2 고정(`FREEZE_V2`, 10-19 18:11) → 1회 평가 | 예비 52 | 이후 규칙을 바꾸지 않음 |

예비 52장 결과(`rgb_2x`, 정답 gold-v2h). 판독률은 규칙과 무관한 정답 문구 문자 일치율이고, 나머지는 완전 일치 정확도다.

| 항목 | EasyOCR v2 | 혼합 v2 | PaddleOCR v2 | PaddleOCR v1 |
| --- | --- | --- | --- | --- |
| 판독률(전체 문구) | 65.8% | 72.3% | 82.7% | 82.7% |
| 축제명 | 3.9% | 19.2% | 26.9% | 19.2% |
| 일정(시작·종료) | 67.3% | 82.7% | 92.3% | 88.5% |
| 장소(원문 일치) | 23.5% | 56.9% | 64.7% | 52.9% |
| 개최 연도 | 92.0% | 92.0% | 96.0% | 96.0% |
| 회차 | 39.1% | 56.5% | 78.3% | 78.3% |
| 핵심 4필드 모두 | 0.0% | 9.8% | 15.7% | 11.8% |

- **권장 경로는 PaddleOCR(2배 입력) + 규칙 v2**다. 판독률 순서는 test 140장에서도 같다(PaddleOCR 83.4% · 혼합 70.0% · EasyOCR 63.2%).
- v1은 dev에 과적합했다. PaddleOCR 핵심 4필드가 dev 32.1%에서 test 5.3%로 떨어졌다. v2는 test 16.5%, 예비 15.7%로 비슷했다.
- PaddleOCR 2배 입력에서는 예비 포스터 중 v2가 v1보다 나빠진 것이 없다(혼합 경로는 장소 1장이 나빠졌다). 장소가 6:0(정확 McNemar p=0.031)으로 가장 크게 좋아졌다.
- 축제명이 가장 큰 병목이다. 예비 오답 38건 중 34건은 OCR이 제목을 온전히 읽지 못한 경우이고, 규칙이 잘못 고른 경우는 4건이다.
- 기관 목록은 거의 못 뽑는다. 예비 52장 PaddleOCR의 기관(역할·이름) F1은 0.13, 판독 확실 기관만 세면 0.27이다. 정답 기관 100개 중 판독 확실한 것이 32개뿐이라 엔진보다 해상도 한계가 먼저 온다. 문의처(전화번호)는 표본이 적지만(분할당 6~10건) F1 0.71~1.00이다. 두 항목의 정답은 사람이 보지 않은 칸이라 참고 지표다.
- 속도(CPU 단독 측정, test 25장, 장당 중앙값): PaddleOCR 2배 입력 29.0초, EasyOCR 6.7초, 혼합 8.1초. 본 실행에서 PaddleOCR 원본 입력은 16.0초였다.

새 포스터에서 기대할 수 있는 수준(권장 경로, 규칙 고정 뒤 처음 본 예비 52장). 맞힐 확률은 위 표의 PaddleOCR v2 열에 있고(일정은 시작일 96.2%, 종료일 92.3%), 아래 표는 그 불확실성과 틀리는 방식이다.

| 항목 | 맞힐 확률의 95% 구간 | 못 찾음 | 값을 냈을 때 맞을 확률 |
| --- | --- | --- | --- |
| 축제명 | 17–40% | 0.0% | 26.9% |
| 시작일 | 87–99% | 3.8% | 100.0% |
| 종료일 | 82–97% | 3.8% | 96.0% |
| 장소 | 51–76% | 5.9% | 68.8% |
| 개최 연도 | 87–99% | 4.0% | 100.0% |
| 회차 | 58–90% | 17.4% | 94.7% |

검수 6칸 기준으로 포스터 1장당 사람이 고칠 칸은 평균 1.3칸이다. 6칸이 모두 맞은 포스터는 11.5%, 1칸 이하만 고치면 되는 포스터는 63.5%다. TourAPI가 주는 약 443×627px 축제 포스터에 해당하는 값이고, 고해상도 원본이나 공연·전시 포스터에는 그대로 적용되지 않는다.

6.1과 6.2는 포스터 수, 지표(CER 대 필드 완전 일치), 정답 상태, 장비가 모두 달라 수치를 직접 비교하지 않는다. 상세 보고서는 9절에 있다.

### 6.3 가상 기준 문서 ↔ 포스터 대조 실험 (2026-10-20)

서비스의 핵심 흐름(기준 문서에서 표기 기준을 뽑고, 포스터와 항목별로 대조)을 시험했다. 실제 의뢰서·계약서와 포스터 짝이 없어 가상 축제 40세트를 만들었다.

- **데이터**: 가상 축제 40세트(seed 20261020). 포스터는 886×1254 px(디자인 틀 5종 × 8장), 기준 문서는 디자인 용역 표준계약서(산업통상부 고시 제2025-033호, 사용자가 받은 고시 원문 PDF 기준) 전문에 '첨부 1. 개발 세부내역 - 포스터 필수 표기 사항' 표를 붙인 A4 이미지(1240×1754 px PNG)다. 일치 20세트, 불일치 20세트(포스터 한 칸만 다르게: 날짜 하루 밀림 4 · 회차 3 · 장소 3 · 행사명 한 글자 3 · 주관 3 · 문의처 2 · 운영 시간 2).
- **방법**: 이미지 문서에서 표를 뽑는 기능이 아직 없어 기준 문서도 PaddleOCR(6.2와 같은 엔진·설정, 원본 입력)로 읽는다(텍스트 PDF·DOCX용 `app/documents.py`는 쓰지 않았다). 표의 '항목' 칸 옆 문구를 조건 9~10개로 삼고, 포스터 OCR에서 기준 값을 찾아 충족·위반·확인 필요로 판정한다. 확실히 다르게 읽힌 경우만 '위반'(판독 신뢰도 0.90 이상, 라벨 없이 찾은 행사명·문구는 0.93 이상), 못 읽었거나 신뢰도가 낮으면 '확인 필요'다. 로고 같은 시각 조건은 자동 판정하지 않고 항상 '확인 필요'로 넘긴다.

| 지표 | 값 |
| --- | --- |
| 세트 판정 정확도(대조 규칙 r1 → r2 → r3 → r4) | 90.0% → 95.0% → 97.5% → 97.5%(r1·r2는 포스터 3장이 낡은 입력으로 읽힌 OCR 결과, r3부터 다시 읽음) |
| 불일치 탐지(r4) | 20/20, 틀린 항목까지 맞힘 20/20 |
| 일치 세트를 잘못 '위반'(r4) | 1/20 (문서 OCR이 행사명 '걷기'를 '겉기'로 읽음) |
| 같은 OCR 결과로 기준 없이 뽑기(6.2의 규칙 v2) | 행사명 19/40 · 장소 39/40 · 기간 36/40 |
| 같은 OCR 결과로 기준과 대조(일치 세트 '충족') | 행사명 18/20 · 회차 14/14 · 그 밖의 정보 항목 20/20 |
| 처리 시간(CPU, 중앙값) | 기준 문서 58초 + 포스터 39초 = 세트당 약 97초 |

- r2~r4는 이 40세트를 보면서 고친 규칙이라 점수가 낙관적이다. 다른 시드로 만든 새 가상 세트로 다시 재야 한다.
- 기준 값이 있으면 '어느 줄이 행사명인가'를 고르는 규칙 오류가 사라진다. OCR이 못 읽는 글자는 그대로다. 실제 예비 52장에서 OCR이 축제명을 온전히 읽은 포스터는 18장(34.6%)뿐이라, 실제 포스터에서는 '확인 필요'가 많이 남는다.
- 기준 문서 오독이 새 위험이다. 문서 OCR이 행사명을 3/40건 잘못 읽었고(모두 같은 글자 '걷'), 그대로 기준이 되면 맞는 포스터도 '위반'이 된다. 담당자가 기준을 확정하는 '기준 확인' 단계가 꼭 필요하다.
- 진행 상황을 보는 실험용 대시보드(팀 서비스 화면 구성을 따름): `.\.venv\Scripts\python.exe -m app.poster_ocr.sim_dashboard --port 8766`. 상세는 9절의 비교 보고서.

### 시작하기 (Windows PowerShell, Python 3.12)

전체 설치·재현 순서는 [README_BACKUP.md](README_BACKUP.md)에 있다. 자주 쓰는 명령만 적는다.

```powershell
py -3.12 -m venv .venv; .\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest tests -q
.\.venv\Scripts\python.exe -m app.poster_ocr.dashboard --port 8765
.\.venv\Scripts\python.exe -m uvicorn config.asgi:application --host 127.0.0.1 --port 8000
```

- 3번째 줄은 실험 대시보드다. `http://127.0.0.1:8765`, 사람 검토 화면은 `/review`.

- 축제 데이터를 새로 수집할 때만 `.env`에 `DATA_GO_KR_SERVICE_KEY`, `TOURAPI_SERVICE_KEY`를 넣는다. 저장된 결과로 채점·보고서를 다시 만드는 데는 키가 필요 없다.
- 일부 작업 기록·보조 스크립트(`.runtime/poster-ocr/`, `data/runtime/festivals/`, `.claude/launch.json`)에는 원래 PC의 절대 경로가 남아 있다. 다른 PC에서 그대로 다시 돌리려면 경로를 고친다.

## 8. 향후 계획

최종 발표(11.20)까지의 계획(중간 발표 10.16 기준):

| 단계 | 시기 | 주제 | 내용 |
| --- | --- | --- | --- |
| 1단계 | 4주차 | DB · 프론트 · 백엔드 | DB 설계 및 구조, 프론트엔드 React, 백엔드 FastAPI |
| 2단계 | 5주차 | 추가 도메인 · 모델 | 이미지·동영상 처리, 모델 선정 및 학습, 에이전트 구조 추상화 |
| 3단계 | 6주차 | 다중에이전트 연동 | 이미지 구분 에이전트, 문서 구분 에이전트, 슈퍼바이저 에이전트 |
| 4단계 | 7~8주차 | 통합 · 배포 · 테스트 | 인프라 구축, 배포, 통합 테스트 |

- 1단계는 main에서 v1으로 진행 중이다(10-20, 상태는 3절 '주의할 점').
- 발표 3단계의 에이전트(이미지 구분·문서 구분·슈퍼바이저)와 A01–A08의 대응은 팀 문서에 없다.

포스터 OCR 실험의 다음 단계:

1. **VLM 실험**: 같은 정답·지표·분할로 소형 로컬 VLM과 RunPod 중형 모델을 비교한다. 규칙을 만들지 않으므로 모든 분할을 평가에 쓸 수 있다. 가장 먼저 볼 항목은 축제명(장식 글꼴 제목) 판독이다. main에는 이미 소형 VLM 재인식 경로(qwen, Qwen3-VL 4B)가 있고, 팀 5장 비교(2026-10-13)에서 CER 59.8%였다. 설계는 [docs/poster-ocr-vlm-testbed.md](docs/poster-ocr-vlm-testbed.md)(데이터 분할은 posters-v2 이전 계획이고, 실제 분할은 5.2절).
2. **새 확인용 포스터**: 예비 52장은 이미 한 번 썼다. 규칙을 또 고치면 TourAPI 새 포스터 50~100장으로 다시 잰다.
3. **검수 화면 분류**: 값을 냈을 때 맞을 확률이 높은 칸(연도·시작일·회차)은 자동 입력 후 확인만 하고, 낮은 칸(축제명·장소)은 '확인 필요'로 표시한다. 수정 기록은 `human-review` 형식으로 쌓아 정답셋을 늘린다.
4. **가상 대조 실험**: 규칙 r4를 고치지 않고 다른 시드의 새 가상 세트로 다시 잰다. 실제 계약서·포스터 짝으로 같은 대조를 해 보고, 기준 문서를 텍스트 PDF·DOCX로 받는 경로(`app/documents.py`)와 문서 OCR 오독을 비교한다.
5. **팀 결정 필요**: 라벨링 규칙 1.1 승인, 공통 JSON 3.0(2.1의 `poster` 블록을 포스터 추출 표준으로 바꿀지), posters-v2 252장 원본을 팀 저장소에 올릴지.

API 키는 포함하지 않는다(`.env`는 저장소에 없다). 가상환경과 모델 가중치도 넣지 않았다.
