# Decisions API 섀도 실험 준비 (2026-10-21)

**상태: 준비만 끝났고 실제 호출은 아직 안 했다.** 실제 호출은 사용자가 승인하고 터미널에서 `OPENAI_API_KEY`를 직접 설정한 뒤 `--call`을 줄 때만 한다.
기존 판정(sim_check r4)은 바꾸지 않는다. 같은 세트에 모델 답을 옆에 기록해 두고 비교만 한다.

- 대상: 가상 세트 v1(시드 20261020)과 v2(시드 20261021)의 80세트. 기관은 지어낸 이름이고 전화번호 국번은 000이다.
- 실제 계약서와 포스터를 보낼지는 팀 데이터 정책으로 정할 일이다. 이 스크립트는 `data/synthetic/` 밖의 이미지를 보내지 않는다.
- Decisions API는 처리를 미국과 EU에서만 한다. 그래서 국내 데이터를 쓰려면 정책 결정이 먼저 있어야 한다.

## 1. 요청 구성 (세트당 1건)

입력은 이미지 두 장이다. 기준 문서 PNG(1240×1754)와 포스터 PNG(886×1254)를 base64 data URL로, `detail: "original"`을 붙여 넣는다.
안내문에는 "맞춤법이 틀려 보여도 고쳐 읽지 말고 보이는 글자 그대로 판단한다"를 넣었다. VLM이 오타를 그럴듯한 낱말로 바로잡아 읽는 경향을 줄이려는 것이다.

| 문항 | 형식 | 무엇을 묻나 | 세트당 |
|---|---|---|---:|
| (a) 기준 문서 확인 | predicate | 기준 문서 표의 '행사명' 칸에 다음 값이 그대로 적혀 있다: '<문서 OCR 값>'. 행사명 칸은 회차까지 원문 그대로 묻는다. | 8 |
| (b) 줄 고르기 | choice | 포스터에서 '행사 장소' 등을 나타내는 줄을 고른다. 보기는 포스터 OCR 줄과 '해당 줄 없음'이다. **기준 값은 문항에 넣지 않는다.** | 8–9 |
| (c) 직접 판정(비교용) | predicate | 포스터에 다음 '행사 장소' 표기가 그대로 나와 있다: '<기준 값>'. 날짜 형식과 띄어쓰기 차이는 같다고 보고, 글자 하나라도 다르면 거짓이다. | 8–9 |
| (d) 판독 가능 정도 | score(4단계) | 판독 불가 / 일부 판독 / 대체로 판독 / 완전 판독 | 8–9 |

- 항목은 행사명, 회차, 행사 기간, 운영 시간, 장소, 주최, 주관, 문의처, 필수 문구다. 기관 로고는 시각 조건이라 뺐다. 회차가 없는 세트에는 회차 문항이 없다.
- 기준 값은 r4와 같은 문서 OCR 값이다. 실제 서비스에도 정답이 없으므로 일부러 그렇게 했다.
- (b) 보기 값은 `L###` 형태다. 번호는 세트마다 고정된 임의 번호라 위치를 드러내지 않는다. 고른 줄의 OCR 박스는 기록해 두었다가 채점할 때 근거 박스로 되살린다.
- 순서 민감도는 `--order shuffled`로 잰다. 같은 보기 값을 문항마다 시드로 섞어 순서만 바꾸고, '해당 줄 없음'은 두 실행 모두 맨 끝에 둔다.
- 요청 본문에는 `model`, `input`, `questions`만 넣는다. user, metadata 같은 식별 정보는 넣지 않는다.
- 호출 쪽 설정은 다음과 같다.
  - 호스트는 `https://api.openai.com/v1`로 고정했다. `OPENAI_BASE_URL` 환경변수는 따르지 않는다.
  - 자동 재시도는 껐다(`max_retries=0`).
  - 키는 출력하지도, 파일에 쓰지도 않는다. 오류 메시지에 키가 섞이면 `***`로 가린다.
  - .env는 읽지 않는다.

  - 한글은 1음절을 1토큰, 그 밖의 글자는 3글자를 1토큰으로 셌다.
  - 텍스트 토큰의 대부분은 (b) 보기 목록이다. 같은 OCR 줄 목록이 항목마다 반복된다.

- 요청 본문은 `data/runtime/poster-ocr/decisions-shadow/requests/<v1|v2>/<세트>.<ocr|shuffled>.json`에 썼다. Git에서 제외되는 폴더이고 크기는 6.8MB다.
  - 이미지 base64는 바이트 수와 sha256만 남겼다. 그대로 쓰려면 `--full-body`를 준다.
  - 집계는 `dry-run.<순서>.json`에 있다.

## 3. 채점 정의 (`decisions_shadow_score.py`)

정답은 sets.json에서, r4 판정은 `data/runtime/poster-ocr/{sim,sim-v2}/checks`에서 읽는다.

1. **잘못 고친 비율**
   - 일부러 넣은 차이(불일치 항목)에 (c)가 P(true)>0.5를 준 비율이다. 차이를 보지 못하고 '그대로 있다'고 답한 비율이다.
   - 유형별로 내고, 묶음(한 글자 오타 / 숫자 차이 / 다른 낱말)별로도 낸다.
   - 기준 값 자체가 문서 OCR 오독인 항목은 뺀다. v2 S32 행사명이 여기에 해당한다(오타 '풀'과 문서 오독 '겉'이 겹친다).
   - 일치 항목에 P(true)≤0.5를 준 헛경보도 함께 센다.
2. **(a) 문서 OCR 오독 6건**
   - 대상은 v1 S09·S25·S38, v2 S05·S10·S32이고, 모두 '단풍 걷기 축제'의 '걷'을 '겉'이나 '같'으로 읽은 경우다.
   - P(true)<0.5면 잡은 것으로 센다. 맞게 읽은 값에 준 헛경보와 AUROC도 낸다.
   - 오독 목록은 데이터에서 다시 계산하고, 알려진 6건과 같은지 확인한다.
3. **(b) 줄 고르기**
   - 정답 줄은 포스터에 실제로 찍힌 값(sets.json의 poster)을 담은 OCR 줄이다. 모델이 고른 줄이 여기에 들면 맞힌 것이다.
   - 날짜, 시각, 전화번호, 회차는 숫자로 찾는다. 나머지 항목은 문자 일치율 60% 이상인 줄이다.
   - v2 S08 장소 줄은 따로 표시한다. 선택 확률 평균에서 정확도를 빼 과신 정도를 낸다.
4. **AUROC와 보정**
   - (c)와 (a)는 항목 단위로 낸다. 점수는 1−P(true)다.
   - (c)는 세트 단위로도 낸다. 점수는 항목 중 가장 큰 1−P(true)이고, r4의 순서형 판정(위반 1 / 확인 0.5 / 충족 0)과 나란히 놓는다.
   - (c)의 Brier 점수도 낸다.
5. **보기 순서 민감도**
   - 두 실행에서 (b) 답이 바뀐 비율과, 같은 보기의 확률이 얼마나 변했는지 본다.
   - 두 번째 실행은 predicate와 score 문항도 다시 묻는다. 그래서 그 변동(0.5를 넘나드는 비율)은 재실행 변동으로 함께 기록한다.
6. **세 설계 비교**
   - 세트 판정은 '위반이 하나라도 있으면 위반, 정보 항목에 확인 필요가 있으면 확인 필요'로 r4와 같게 만든다. 채점은 `sim_check.evaluate`로 한다.

   | 설계 | 항목 판정 |
   |---|---|
   | 판별 먼저 | 모델 신호가 항목을 정한다. r4는 쓰지 않는다. |
   | 확인 필요만 2차 의견 | r4의 충족과 위반은 그대로 둔다. r4가 '확인 필요'로 넘긴 항목만 모델 신호로 정하고, 모델도 애매하면 그대로 둔다. |
   | 병렬로 올리기만 | 판정은 r4 그대로다. 모델 의견만 띄운다. r4와 반대인 '플래그'가 맞는 지적인지 잡음인지, r4 '확인 필요' 항목에 대한 제안이 맞는지 센다. |
   | (참고) r4 + 기준 문서 확인 | (a)가 P(true)<0.5를 준 항목의 r4 '위반'을 '확인 필요'로 보류한다. S05 같은 오탐을 겨냥했다. |

   - 모델 신호는 두 가지다.
     - **(c) 직접 판정**: P(true)≥충족선이면 충족, ≤위반선이면 위반, 그 사이는 확인 필요다. 근거 박스가 없다.
     - **(b) 줄 고르기 + r4 규칙**: 고른 줄과 그 이웃 줄만 놓고 r4 판정 함수를 다시 돌린다.
       - 라벨이 없는 줄이라도 모델이 그 줄을 항목으로 짚었고 판독 신뢰도가 0.90 이상이면 '다름'(위반)으로 본다. 이때 선택 확률은 0.5 이상이어야 한다.
       - 근거 박스로 OCR 줄 박스가 남는다.
   - (c) 임계값은 우리 정답으로 정하고, 두 가지를 낸다.
     - `fixed_0.5`: 0.5 한 선이다.
     - `cross`: 다른 데이터셋 정답으로 정한 선이다. v1으로 정해 v2에 쓰고, 반대로도 한다.
       - 충족선은 보정 세트의 실제 불일치가 하나도 넘지 않는 선이고, 위반선은 실제 일치가 하나도 내려가지 않는 선이다.
       - 두 무리가 완전히 갈리면 가운데 한 선을 쓴다.
   - 표에는 '모델이 정한 항목'과 그중 '근거 박스 없음'을 함께 적는다. API가 근거 위치를 돌려주지 않으므로, (c) 신호로 정한 항목은 모두 박스 없이 판정한 것이다.

## 4. 모델 없이 미리 본 상한

정답을 모델 답 자리에 넣어 계산했다. (b)에는 정답 줄을, (a)에는 문서 OCR이 맞으면 1, 틀리면 0을 넣었다. `--oracle`로 다시 만들 수 있고 호출하지 않는다.
모델이 다 맞혀도 각 설계가 낼 수 있는 최선이다.

| 데이터셋 | 설계 | 정확도 | 재현율 | 정밀도 | 확인 필요 세트 | r4와 달라진 항목 |
|---|---|---:|---:|---:|---:|---|
| v1 | r4 그대로 | 97.5% | 100.0% | 95.2% | 1 | |
| v1 | 판별 먼저 / 2차 의견 (정답 줄) | 97.5% | 100.0% | 95.2% | 1 | 없음 |
| v1 | r4 + 기준 문서 확인 (정답) | 100.0% | 100.0% | 100.0% | 2 | S09 행사명 위반 → 확인 필요 |
| v2 | r4 그대로 | 92.5% | 90.0% | 94.7% | 5 | |
| v2 | 판별 먼저 / 2차 의견 (정답 줄) | 95.0% | 95.0% | 95.0% | 4 | S08 장소 확인 필요 → 위반 |
| v2 | r4 + 기준 문서 확인 (정답) | 92.5% | 85.0% | 100.0% | 7 | S05 행사명 위반 → 확인 필요(오탐 제거), S32 행사명 위반 → 확인 필요(진짜 오타를 놓침) |

- **S08**: 라벨 없는 장소 줄도 위치만 맞게 짚으면 r4 규칙이 '다름'을 가른다. 그래서 (b)는 S08을 고칠 수 있는 구조다. 실제로 고치는지는 모델이 그 줄을 고르는지에 달렸다.
- **S13**: 정답 줄을 줘도 확인 필요로 남는다. (b)+규칙은 글자를 OCR에서 가져오는데, OCR이 오타 '국홤향'을 '국황향'으로, 0.89로 읽었기 때문이다.
  - 이 사례를 모델이 바꿀 수 있는 길은 (c)뿐이다.
  - 그러나 (c)는 오타를 바로잡아 읽을 위험이 가장 큰 문항이다. '잘못 고친 비율'에서 한 글자 오타 행을 봐야 하는 이유다.
- **S05**: 줄 고르기로는 고칠 수 없다. 기준 값 자체가 틀렸기 때문이다. (a)가 오독을 잡으면 오탐을 보류로 돌릴 수 있다.
  - 대가가 있다. v2 S32처럼 진짜 오타와 문서 오독이 겹친 세트도 보류되어, 재현율이 내려간다.
- 같은 판정 코드는 별도 임시 폴더에서 지어낸 응답으로 처음부터 끝까지 돌려 보았다. 이 점검 수치는 보고하지 않는다.
  - 확인한 것은 모든 표가 채워지는지, r4 기준선(v1 97.5%, v2 92.5%)이 그대로 나오는지다.

## 5. 해석할 때 주의

- 표본이 작다.
  - 데이터셋마다 40세트이고 불일치는 20세트다. 세트 하나가 2.5%p, 불일치 세트 하나가 재현율 5%p를 움직인다.
  - 유형별 불일치 항목은 2–6개뿐이다.
  - `cross` 임계값은 오답이 0이 되게 고른 선이라, 극단값 하나에 크게 흔들린다.
- v1은 r4 규칙을 맞출 때 본 세트다. 홀드아웃은 v2뿐이다.
- 근거가 있는 판정이 무엇인지 구분해야 한다.
  - (c)와 (a)가 정한 판정에는 근거 위치가 없다. 담당자는 이미지를 직접 다시 봐야 한다.
  - (b)+규칙은 OCR 줄 박스를 근거로 남긴다.
- 공개 정보가 부족하다.
  - 확률 보정 수치가 공개되지 않았다. 커뮤니티 테스트에서는 choice 확률이 과신하고 보기 순서에 흔들렸다.
  - 그래서 결과에서 과신 정도와 순서 민감도를 먼저 본다.
- 요청 필드 이름은 OpenAI 가이드와 공개 튜토리얼을 따랐다. 공식 API 레퍼런스 페이지는 이 환경에서 열리지 않았다.
  - 따른 필드는 `questions[].type/name/instructions`, choice의 `choices[{value, description}]`, score의 `levels[{label, description}]`, `input_image.image_url`이다.
  - `detail: "original"`은 가이드에 나오지 않는다. 그래서 거부될 수 있다.
  - 거부되면 첫 세트에서 `<세트>.<순서>.error.json`을 남기고 멈춘다. 재시도는 하지 않는다.
  - 응답의 `probabilities`는 목록이든 사전이든 받도록 했다.

```powershell

.\.venv\Scripts\python.exe -m app.poster_ocr.decisions_shadow
.\.venv\Scripts\python.exe -m app.poster_ocr.decisions_shadow --order shuffled
# 2) 호출 준비: 패키지 설치. 키는 사용자가 이 터미널에서 직접 설정한다(파일에 쓰지 않는다)
.\.venv\Scripts\python.exe -m pip install -r requirements-decisions.txt
# 3) 한 세트로 먼저 확인(약 $0.001)
.\.venv\Scripts\python.exe -m app.poster_ocr.decisions_shadow --call --dataset v2 --set S08
# 4) 전체 80세트 → 보기 순서 바꾼 80세트(각 약 $0.07)
.\.venv\Scripts\python.exe -m app.poster_ocr.decisions_shadow --call
.\.venv\Scripts\python.exe -m app.poster_ocr.decisions_shadow --call --order shuffled
# 5) 채점
.\.venv\Scripts\python.exe -m app.poster_ocr.decisions_shadow_score --md docs/reports/decisions-shadow/results.md
```

- 이미 받은 세트는 건너뛴다. 다시 받으려면 `--force`를 준다.
- 실패하면 바로 멈춘다. 다음 세트로 계속 넘어가려면 `--keep-going`을 준다.
- 응답 원본은 `data/runtime/poster-ocr/decisions-shadow/<v1|v2>/<세트>.json`에 저장된다. 순서를 바꾼 실행은 `<세트>.shuffled.json`이다.
  - 응답 전체(model, usage, answers의 probability·choice·probabilities·confidence·score·refusal)가 들어간다.
  - 요청 ID와 채점에 쓰는 문항 기록(meta)도 함께 들어간다.

## 7. 파일

- `app/poster_ocr/decisions_shadow.py`: 요청 생성, dry-run, `--call`
- `app/poster_ocr/decisions_shadow_score.py`: 채점과 `--oracle` 상한
- `tests/test_decisions_shadow.py`: 19개, 호출 없음
  - 요청 형식, 순서 섞기, 토큰 추정을 확인한다.
  - 키가 없으면 거부하는지, 키가 기록되지 않는지, 재시도가 꺼졌는지, 호스트가 고정됐는지 확인한다.
  - 채점 지표와 설계 비교를 확인한다.
- `requirements-decisions.txt`: `openai>=3.26.0`. `--call`에만 필요하다.
