결론

  • 같은 OCR 결과라도 '기준 문서와 대조'하면 '기준 없이 뽑기'보다 행사명이 훨씬 잘 맞는다. 가상 포스터 40장에 기존 규칙 v2를 그대로 돌리면 행사명은 47.5% (19/40)만 맞았다(장소 97.5% (39/40), 기간 90.0% (36/40)). 같은 OCR 결과에서 문서의 행사명을 찾으면 일치 세트 90.0% (18/20)을 '충족'으로 확인했다. 차이는 OCR이 아니라 '어느 줄이 행사명인가'를 고르는 단계에서 나온다(여러 줄로 나눈 행사명의 한 줄만 고름).
  • 실제 포스터에서는 대조로도 판독 한계를 넘지 못한다. 실제 예비 52장의 축제명은 14장을 맞혔고, OCR이 제목을 완전히 읽었는데 규칙이 못 고른 4장을 더해도 34.6% (18/52)가 상한이다. 나머지 34장은 제목을 일부만 읽었거나 못 읽었다. 대조는 줄 고르기 오류를 없애지만, 이런 포스터는 '확인 필요'로 남는다.
  • 가상 40세트의 세트 판정 정확도는 90.0%(r1) → 95.0%(r2) → 97.5%(r3) → 97.5%(r4)다. 첫 실행 뒤의 값은 모두 같은 40세트를 보고 고친 것이라 낙관적이다. 현재 규칙으로 불일치 20세트 중 20세트를 '위반'으로 잡았고, 일치 20세트 중 1세트를 잘못 '위반'으로 판정했다.
  • 새로운 실패 유형은 기준 문서 오독이다. 문서 OCR이 행사명을 3건 잘못 읽었고('걷기'→'겉기'·'같기'), 그대로 기준이 되면 맞는 포스터도 '위반'이 된다. 모두 '단풍 걷기 축제' 한 주제의 '걷' 한 글자(맑은 고딕 23px)에서 나온 체계적 오독이고, 문서 OCR 신뢰도로는 가려낼 수 없었다. 문서에서 뽑은 기준을 담당자가 확정하는 단계(팀 서비스의 '기준 확인')가 꼭 필요하다.
  • 두 차례 독립 검증에서 수치를 바꾼 구현 결함을 찾아 고쳤다. 1차: 포스터 3장이 낡은 입력 이미지로 읽혔고, 큰 배경 숫자가 행사명 첫 낱말과 한 줄로 묶였고, 장식 문장부호가 판독 신뢰도를 끌어내렸다. 2차: 글자 없는 줄이 행사명 창을 끊었고, 라벨 옆 문구에서 낱말 하나를 못 읽은 경우가 '위반'이 됐고, 겹친 OCR 박스가 같은 글자를 두 번 넣었다. 고친 뒤 정보 항목 '확인 필요'는 2건(기준 문서 안 행사명 표기가 서로 다름)만 남았다.
  • 처리 시간은 세트당 약 97초(CPU)다. 기준 문서 58초, 포스터 39초(중앙값). 포스터는 실제 실험의 2배 입력과 같은 886×1254 px이고, 실제 본 실행의 2배 입력 중앙값 37.9초와 비슷하다. 실제 실험의 29.0초는 다른 작업 없이 따로 잰 값이다.

검증에서 고친 것

결과를 정리하기 전에 독립 검증을 두 차례 돌려 정답·판정·채점과 대시보드를 따로 확인했다. 1차 검증(r3에서 수정)에서 찾은 세 가지는 수치를 바꾼 구현 결함이다.

  • 낡은 입력 이미지: OCR 실행기가 예전 실행의 입력 캐시(.runtime/poster-ocr/inputs)를 다시 써서, 포스터 3장(S03·S05·S08)이 고치기 전 디자인으로 읽혔다. 입력을 매번 원본에서 새로 만들고 결과에 원본 해시를 남기도록 고친 뒤 3장을 다시 읽었다.
  • 줄 묶기: 높이 비교 조건이 늘 참이라, 타이포 틀의 큰 배경 숫자(높이 약 360px)가 행사명 첫 낱말과 한 줄이 됐다. 글자 높이가 비슷하고 세로로 겹치는 박스만 묶도록 고쳤다.
  • 판독 신뢰도: 창 안 모든 박스의 최솟값을 써서 별 장식의 문장부호 박스(0.16~0.24)가 섞였다. 글자가 있는 박스만으로 계산하도록 고쳤다.

2차 검증(r4에서 수정)은 정확도는 그대로였지만 근거 문구와 판정 사유를 바꿨다.

  • 글자 없는 줄: 장식에서 나온 문장부호만 있는 줄이 행사명 줄 사이에 끼어 S38 행사명 창을 끊었다. 글자·숫자가 없는 줄은 대조에서 뺀다.
  • 라벨 옆 낱말 누락: 장소·주최·주관을 라벨 옆 문구로 비교할 때, 낱말 하나를 못 읽은 경우도 '위반'이 됐다. 다른 글자 없이 낱말만 빠졌으면 '확인 필요'로 둔다. 기간·회차도 판독 신뢰도가 낮으면 '위반' 대신 '확인 필요'다.
  • 겹친 OCR 박스: 같은 글자를 두 박스가 겹쳐 읽어 S01 슬로건에 글자가 한 번 더 들어갔다. 겹친 폭만큼 신뢰도가 낮은 쪽 글자를 빼고 잇는다.
  • OCR 실행기: 이미 있는 결과는 원본 해시가 같고 성공한 경우에만 건너뛰고, 결과는 다 쓴 뒤 바꿔 넣으며, 실행마다 기록을 남긴다(runs.jsonl). 기존 결과 77건에는 입력 해시를 확인한 뒤 원본 해시를 채웠다.

그 밖에 대시보드의 연결 오류 표시, OCR 실패·원본 변경·작업자 정지 표시(실패가 있으면 '완료'로 보이지 않음), 세트 요약 문구(팀 서비스에 없는 표시임을 밝힘), 좁은 화면 배치, Host 검사 등을 고쳤다. 정답 파일의 포스터 정식 명칭 6건도 바로잡았다(이미지는 같음).

왜 결과가 다른가

  • 데이터: 실제 포스터는 약 443×627 px로 줄어든 이미지라 작은 글자와 장식 글꼴을 읽기 어렵다. 가상 포스터는 실제 포스터의 2배 크기(886×1254 px)로 그린 표준 글꼴이라 OCR이 거의 다 읽는다.
  • 과제: 기준 없이 '어느 큰 글자가 축제명인가'를 고르는 일은 어렵지만, 기준 문서의 값이 있으면 그 값이 포스터에 있는지만 찾으면 된다. 서비스의 핵심 흐름(기준 확정 → 대조)은 규칙의 줄 고르기 오류를 없앤다. OCR이 못 읽은 글자(판독 한계)는 그대로 남는다.
  • 새 위험: 기준 자체를 OCR로 읽으면 기준 오독이 그대로 오탐이 된다. 실제 의뢰서·계약서는 표가 더 복잡하므로 이 위험은 더 커진다.
  • 판정 원칙: 확실히 다르게 읽힌 경우만 '위반', 못 읽었거나 불확실하면 '확인 필요'로 둬서, 자동 판정의 실수가 담당자 확인으로 넘어가게 했다. 다만 기준 자체가 틀리면(S09) 이 원칙으로도 막을 수 없다.

한계와 다음 단계

  • 첫 실행 뒤의 규칙(r2~r4)은 모두 같은 40세트를 보고 고쳤다. 다른 시드의 새 가상 세트(20~40세트)로 다시 재야 한다.
  • 가상 포스터는 실제보다 깨끗하다. 실제 포스터와 실제 의뢰서·계약서 짝으로 같은 대조를 해 봐야 서비스 성능을 말할 수 있다.
  • 기준 문서 오독은 기준 확인 화면에서 담당자가 확정하도록 하고, 행사명처럼 반복되는 값은 문서 안 표기를 함께 보여 준다.
  • 장식 글꼴 제목은 VLM(소형 로컬·RunPod 중형) 재인식 후보로 비교한다.
