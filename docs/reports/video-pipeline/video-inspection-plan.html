01 · 먼저 바꿀 것

원안에서 먼저 바꿀 다섯 가지

각 항목은 main 코드를 직접 돌려 보거나 공식 문서로 확인한 결과입니다. 나머지 단계별 내용은 이 다섯 가지를 전제로 합니다.

원안확인한 사실바꾸는 방법
1구간마다 대표 프레임을 포스터처럼 검수 review_criteria는 문구를 못 찾으면 '확인 필요'를 냅니다. 구간별로 돌리면 문구가 없는 구간 대부분이 '확인 필요'가 됩니다. '함께 즐기는 축제' 같은 자막만 있는 구간은, 기준이 '행사명: …축제' 형식이고 그 자막을 0.97 이상 신뢰도로 읽으면 행사명이 위반으로 나옵니다. 재현 기준은 영상당 1회, 같은 자막을 묶은 '자막 트랙' 전체로 판정합니다. 구간은 근거 위치를 보여 주는 단위로만 씁니다.
2OCR 장당 0.5~2초, 1분 영상 30초~2분 지금 paddle-only는 이미지마다 하위 프로세스를 띄우고 모델을 새로 올립니다. 장당 6.90초 실측 Mac 포스터. 60초 영상 84프레임이면 OCR만 약 9.7분(84 × 6.90초 계산)이고, 그동안 포스터 검수도 멈춥니다. 모델을 한 번만 올려 여러 프레임을 읽는 배치 모드를 추가합니다. OCR 47~174초, 전체 약 63~193초 추정
3앞 프레임과 pHash가 가까우면 OCR 생략 전체 프레임 pHash는 자막만 바뀐 화면을 구분하지 못합니다. '할인 50%→70%'의 해밍 거리가 0/64입니다. 실측 MVP는 1초 프레임을 전부 OCR합니다. 생략은 2~4fps로 올릴 때 OCR 박스 기준으로 다시 설계합니다.
4광고·협찬 표기가 영상 어딘가에 있는지 공정위 예규 제499호는 동영상 표시를 제목 또는 영상 안에 두고, 영상 안이면 시작부분과 끝부분에 넣고 반복하라고 합니다. 'AD', 'Thanks to', '체험단'은 부적절한 표현입니다. 축제 엔딩의 '협찬: ○○' 크레딧은 표시문구가 아닙니다. 공식 별도 모듈 video_disclosure.py가 적용 대상, 문구, 위치를 판정합니다. 시작·끝 3초는 0.2초 간격으로 다시 읽습니다.
5EmbeddingGemma 2로 같은 항목을 한 번 더 확인 모델은 실재합니다(2026-10-06, Apache 2.0, 740M). 하지만 공식 예제에서 관련 문구와 무관한 문구의 유사도 차이가 약 0.1(0.641 대 0.534)이고, 작은 한국어 글자에 대한 평가가 없습니다. 공식 기본은 꺼 둡니다. 45회 스모크로 광고 표시 점검을 계속할지 먼저 가리고, 켜는 것은 점검별 본 시험과 2주 기록 운영을 통과한 뒤입니다. 결과는 '확인 필요'와 구분해 '이중 검수 엇갈림'으로 표시합니다.

원안의 사실관계 중 함께 고칠 것

  • ffmpeg -vf fps=1의 frame_0012.jpg는 12초 화면이 아닙니다. 반올림 기본값(round=near)과 번호 시작값(1) 때문에 11.5초 직전 프레임이 됩니다. 30fps 영상에서는 11.467초 화면이었습니다. 실측
  • PySceneDetect는 자막만 바뀐 지점을 13번 중 0번 잡았고, 1초 디졸브도 잡지 못했습니다. 하드컷 전용 신호입니다. 실측
  • 현재 판정 규칙에는 오탈자 판정이 없습니다. 일반 문구 기준은 글자가 다르면 '근거 없는 확인 필요'가 됩니다. '위반'은 기간과 '…축제/…페스티벌' 행사명 기준에서만, 그것도 Paddle 점수 0.97 이상일 때만 나옵니다. 광고 표기가 없어도 지금 규칙으로는 위반이 나오지 않습니다.
  • 기존 업로드(POST /api/reviews)는 PIL로 정지 이미지만 받습니다. 20MiB를 넘는 MP4는 413, 그 이하는 415로 거부되고, 업로드는 메모리로 통째 읽습니다.
  • 화면 용어는 '충족·위반·확인 필요'입니다. 원안의 '미충족'과 맞춰야 합니다.
  • 기획서는 영상을 '약 30초, P2'로 두고, README도 영상 검수를 이미지 검수 이후 과제로 둡니다. 일정 판단이 먼저 필요합니다.

FRAME_POLICY = {"base_step_ms": 1000, "window_step_ms": 200, "head_ms": 3000, "tail_ms": 3000,
                "rule": "last_frame_with_pts_le_slot", "autorotate": True,
                "max_long_side": 1920, "jpeg_quality": 90}


def sample_slots(duration_ms: int, policy: dict = FRAME_POLICY) -> dict[int, list[str]]:
    """1초 격자와 시작·끝 3초 0.2초 창을 합친다. 겹치는 시각은 태그만 늘린다."""
    step = policy["window_step_ms"]
    slots = {t: ["base"] for t in range(0, duration_ms, policy["base_step_ms"])}
    for t in range(0, min(policy["head_ms"], duration_ms), step):
        slots.setdefault(t, []).append("head")
    tail_start = -(-(duration_ms - policy["tail_ms"]) // step) * step   # 판정 창 [d-3000, d)와 맞춤(올림)
    for t in range(max(0, tail_start), duration_ms, step):
        slots.setdefault(t, []).append("tail")
    return dict(sorted(slots.items()))

# sample_slots(60000) → 84개(base 60), sample_slots(90000) → 114개 (실행 확인)

파일명은 f"t{time_ms:06d}.jpg"입니다. 6자리라 999,999ms(약 16분)까지 표현됩니다. 끝 창 시작을 올림으로 잡아 영상 길이가 200ms 배수가 아니어도 'tail' 프레임이 모두 판정 창 안에 들어갑니다.

바뀌는 점결과는 하드컷 후보로만 씁니다. 자막 변화는 4단계가 잡습니다.

할 일

  1. scenedetect-headless==0.7.2를 설치합니다. 일반 scenedetect는 opencv-python을 끌어와 프로젝트의 opencv-python-headless==5.0.0.93과 충돌합니다. 0.7.1은 av==19.0.1과 함께 쓰면 오류가 나므로 두 버전을 묶어 관리합니다. 실측
  2. AdaptiveDetector(min_scene_len='0.5s'), backend='pyav'(14.4초 → 8.1초), get_scene_list(start_in_scene=True)로 컷이 없어도 전체를 한 장면으로 받습니다. 시각은 .seconds를 씁니다(get_seconds()는 폐기 예정).
  3. pyav 백엔드는 스트림 시작 시각을 빼고 보고하므로 컨테이너 기준 ms로 되돌립니다. 0.5초 늦게 시작하는 파일에서 500ms 차이가 났습니다. 실측
  4. 컷 시각 이후 첫 1초 프레임을 경계(grid_ms)로 둡니다. 1초 안의 컷 두 개는 하나로 합치고, 그 사이의 짧은 장면은 unsampled_scenes에 기록합니다.
  5. 장면 검출이 실패해도 검수는 멈추지 않습니다. scenes.status='failed'와 경고만 남기고 계속합니다.

지금 코드로 돌리면

recognize_paddle()은 이미지 1장마다 paddle_full_worker 하위 프로세스를 띄우고, PaddleOCR 모델을 새로 만들고, 모델 파일 SHA-256 검증을 3번 합니다. 포스터(2배 입력) 실측이 장당 6.90초, 작업자 최대 메모리 8.15GiB입니다 실측 Mac M4 Pro. 84프레임이면 약 580초(84 × 6.90초 계산)이고, 그동안 inference_lock을 잡아 포스터 검수도 대기합니다.

할 일

  1. paddle_full_worker.py에 --manifest 모드를 추가합니다. 모델은 한 번 만들고, 프레임마다 predict 후 JSONL 한 줄을 바로 기록합니다. 기존 --input 모드와 테스트 27건은 그대로 둡니다.
  2. paddle_ocr.recognize_paddle_frames()를 추가합니다. 해시 검증은 배치당 3회(0.23초)로 줄입니다. 한 프레임의 예외·좌표 이상·멈춤은 그 프레임만 실패로 남깁니다. 지금은 레코드 하나만 이상해도 호출 전체가 실패합니다.
  3. 프레임을 원래 크기로 넣습니다. text_det_limit_side_len=1280 때문에 1080×1920은 1배든 2배든 탐지 입력이 704×1280으로 같습니다(PaddleX 축소 규칙으로 계산). 2배 확대는 인식 crop에만 영향을 주고(소스 기준 추론), 프레임당 1.48초(확대+PNG 저장)를 더합니다 실측.
  4. 좌표는 프레임 픽셀 그대로 쓰고(÷2 없음), 레코드 ID는 t012000:paddle_003처럼 프레임을 붙여 영상 전체에서 유일하게 만듭니다. 그대로 합치면 Duplicate record id: paddle_000 오류가 납니다.
  5. 정규화한 결과를 ocr/frames.jsonl(프레임당 1줄)에 씁니다. 다음 단계는 이 파일만 읽습니다. 프레임별 탐지 상자 점수(dt_scores)와 글자가 빈 상자도 함께 남겨, 나중에 '글자를 못 읽음' 점검에 씁니다. 성공 비율이 0.9 미만이면 failed_stage='ocr'로 끝냅니다.
  6. 영상 성격이 '광고주 자체 광고'(광고 표시 적용 대상 아님)이면 시작·끝 창 전용 24장은 OCR하지 않고 skipped로 기록합니다(12~48초 절약 추정).
  7. Windows에는 resource 모듈이 없어 지금은 메모리가 null로 남습니다. 표준 라이브러리 ctypes로 최대 작업 집합(PeakWorkingSetSize)을 기록합니다.
  8. 팀 PC에서 측정합니다: 탐지 한도 1280 대 1920(탐지 픽셀 2.32배), cpu_threads 4 대 논리 코어 수, enable_mkldnn(Paddle 3.3 CPU 오류 보고, PaddleOCR 이슈 #17539).

def run_batch(manifest_path, output_path, detection_dir, recognition_dir):
    """모델을 한 번 만들고 프레임마다 결과 한 줄을 JSONL에 즉시 기록한다."""
    _prepare_environment()
    frames, settings = read_manifest(manifest_path)
    identities = {"detection": verify_model(detection_dir, DETECTION_MODEL),   # 배치당 1회
                  "recognition": verify_model(recognition_dir, MODEL)}
    started = time.perf_counter()
    from PIL import Image
    import paddle
    model = _build_model(detection_dir, recognition_dir, **settings)   # 기존 생성 인자 그대로
    with Path(output_path).open("x", encoding="utf-8") as stream:
        def emit(value):
            stream.write(json.dumps(value, ensure_ascii=False, allow_nan=False) + "\n")
            stream.flush()
            os.fsync(stream.fileno())

        emit({"type": "start", "device": paddle.get_device(), "model_identity": identities,
              "load_seconds": time.perf_counter() - started, "frame_count": len(frames)})
        for frame in frames:
            tick = time.perf_counter()
            try:
                with Image.open(frame["path"]) as opened:
                    dimensions = list(opened.size)
                outputs = list(model.predict(input=frame["path"]))
                if len(outputs) != 1:
                    raise ValueError("Expected exactly one Paddle OCR image result")
                raw = outputs[0].json
                raw = json.loads(raw) if isinstance(raw, str) else raw
                emit({"type": "frame", "id": frame["id"], "status": "ok", "input_dimensions": dimensions,
                      "inference_seconds": time.perf_counter() - tick, "raw": raw})
            except Exception as exc:  # 한 프레임의 예외로 남은 프레임을 버리지 않는다
                traceback.print_exc()
                emit({"type": "frame", "id": frame["id"], "status": "failed",
                      "error_type": type(exc).__name__})
        emit({"type": "end", "peak_rss_bytes": _peak_memory_bytes()})

발췌입니다(전체는 직렬화 실패 처리와 프레임별 메모리 기록 포함). 부모 쪽은 0.5초마다 새 줄을 읽어 진행률을 갱신하고, start 줄의 device·model_identity를 사후 해시와 대조하며, 60초 동안 새 줄이 없으면 그 프레임을 멈춤으로 처리합니다.

GPU로 돌릴 때는 paddle.get_device() 대신 요청 장치와 GPU 진단 정보를 기록합니다. paddle.get_device()는 전역 기본값이라 실제 추론 장치가 아닙니다. 장치 선택, 카나리, CUDA 오류 처리는 05 GPU를 쓰면을 따릅니다.

할 일

  1. text_changed(a, b): 숫자·% 토큰은 정확히 비교하고, 나머지는 자모 편집거리로 봅니다. 허용 편집 수는 min(3, max(1, round(0.15×자모 길이))), 4자모 미만은 0입니다. 숫자 옆의 O·I는 비교 키에서만 0·1로 접습니다(원문은 그대로).

  5. 구간 경계 = 장면 컷 ∪ 보이는 트랙 집합이 바뀌는 프레임. 1프레임짜리 트랙만으로 생긴 경계는 지웁니다(표시용이라 판정에는 영향 없음).

NUMBER = re.compile(r"\d+(?:[.,]\d+)*%?")
DIGIT_RUN = re.compile(r"[0-9Oo〇Il|]*[0-9][0-9Oo〇Il|]*")
DIGIT_FOLD = str.maketrans({"O": "0", "o": "0", "〇": "0", "I": "1", "l": "1", "|": "1"})
JAMO_RATIO, JAMO_MAX_EDITS, JAMO_MIN_LEN = 0.15, 3, 4


def text_key(text: str) -> str:
    """review_rules.normalized 결과에서 숫자에 붙은 O/I만 0/1로 접은 비교 키."""
    return DIGIT_RUN.sub(lambda m: m.group().translate(DIGIT_FOLD), normalized(text))


def text_changed(a: str, b: str) -> bool:
    key_a, key_b = text_key(a), text_key(b)
    if NUMBER.findall(key_a) != NUMBER.findall(key_b):
        return True                                   # 숫자는 정확히
    rest_a = unicodedata.normalize("NFD", NUMBER.sub("", key_a))
    rest_b = unicodedata.normalize("NFD", NUMBER.sub("", key_b))
    longest = max(len(rest_a), len(rest_b))
    allowed = 0 if longest < JAMO_MIN_LEN else min(JAMO_MAX_EDITS, max(1, round(JAMO_RATIO * longest)))
    return Levenshtein.distance(rest_a, rest_b) > allowed   # 한글은 자모로

# 할인 50%/할언 50% → False · 할인 50%/할인 70% → True · 할인 5O%/할인 50% → False
# 특가/특가! → False · 3,000원/13,000원 → True · 행사/축제 → True   (실행 확인)

할 일

  1. 트랙을 판정 레코드로 바꿉니다: {id:'trk_0003', text: 투표 문구, confidence: 트랙 신뢰도, bbox_xyxy, recognition_engine:'paddleocr'}.

GPU를 쓸 때의 위험

  • Windows + sm_120은 오류 없이 틀린 결과를 낼 수 있습니다. cu126 이하 휠은 경고만 내고 1/3=0 같은 잘못된 연산을 했고(#73937), cu129 3.3.1에서도 RTX 5060 노트북에서 탐지 0개라는 미해결 보고가 있습니다(#79354). 빈 OCR은 6-A의 '표시 흔적 없음'과 맞물려 거짓 위반이 됩니다. 카나리와 대조 게이트가 막습니다.
  • 공식 문서가 엇갈려 보입니다. PaddleOCR 설치 문서의 'Windows 50 시리즈 미지원' 경고는 그 문서가 안내하는 3.2.0 cu118·cu126 설치에 대한 것입니다. cu129 3.3.1 Windows 휠은 인덱스에 있지만(실측), Windows에서 PP-OCRv5를 검증한 공식 기록은 없습니다. 그래서 실행 검증 전까지 미검증으로 봅니다.
  • CPU와 GPU 판정이 달라질 수 있습니다. TF32 기본 허용과 cuDNN 비결정성 때문에 0.97 경계 근처 레코드가 뒤집히면, GPU에서 통과한 Gate C가 CPU 운영에서 깨집니다.
  • 장치 기록이 틀어질 수 있습니다. paddle.get_device()는 전역 기본값이고, _safe_runtime은 gpu:0을 조용히 버리며, Windows에서 requirements.txt만 설치하면 CPU torch가 들어가 'GPU 수치'가 실제로는 CPU 값일 수 있습니다.
  • 12GB VRAM에서 탐지 1920(공식 min1280 계열 10~13.5GB), 이중 검수 batch 32, whisper batch 8, 화면 출력이 겹치면 OOM이 납니다. sysmem fallback이 켜져 있으면 오류 없이 느려지기만 해서 시간 측정을 믿을 수 없습니다.
  • RunPod은 세 후보 모두 한국·일본 리전이 없습니다(국외 이전, 고객 NDA). 청크 분할은 '제출 결과 불명' 위험을 청크 수만큼 늘리고, 콜드 스타트 꼬리(이미지 pull 수 분)가 길면 1건 단위로는 로컬 CPU보다 느릴 수 있습니다.
  • 개인 PC를 팀 서버로 열면 안 됩니다. POST /api/reviews에 인증이 없고(api.py:657), 결과는 ID만 알면 읽힙니다(api.py:726-735). 포트포워딩, 0.0.0.0 바인딩, trycloudflare, Tailscale Funnel은 공개 노출입니다. 측정과 환경이 한 사람에게 묶이는 문제도 있습니다.

  • 시간이 남으면: E3 흐리거나 작은 줄만 crop 2배 재인식(미달 범주가 있을 때 우선) · E4 CLAHE 대비 보정 · E5 적응 이진화 · JPEG q85/q90/q95 비교 · P1 투표 방식 · P3 트랙 신뢰도 중앙값/최대/최소 · T1 cpu_threads 8 · T2 enable_mkldnn · T3 시작·끝 창은 1초 프레임에서 표시를 못 찾았을 때만 OCR. 문구가 같거나 정확도가 나빠지지 않을 때만 채택합니다.

GPU를 함께 쓰면 바뀌는 검증

  • 장치별 측정표: 장치 열은 CPU-T(팀 PC), CPU-P(5070 PC의 CPU 경로), GPU-P(5070), GPU-R(RunPod, GPU 이름 표기)입니다. 공통 열은 OS, CPU, RAM, GPU(노트북 여부), 드라이버, CUDA·cuDNN, paddle·paddleocr·paddlex 버전, precision, TensorRT 끔, 탐지 한도, fps, 프레임 수, load_s, frame_p50, ocr_total_s, e2e_p50, peak_rss, peak_vram, sysmem fallback, CER, 게이트 판정입니다.
  • E0-GPU 대조(신규): 같은 frames.json(sha256 동일), 같은 model_identity, 같은 OCR 인자로 FP32·TensorRT 없이 CPU-T와 GPU-P를 돌립니다. 대조 때는 NVIDIA_TF32_OVERRIDE=0, FLAGS_cudnn_deterministic=1을 켭니다. 지표는 문구 완전일치율, |Δ신뢰도| p99, bbox IoU, 0.97·0.6·0.5 경계를 넘나든 레코드 수, 탐지 0개 프레임 비율입니다. 통과는 results[].status와 광고 표시 판정 차이 0건이고, CER 허용폭은 팀이 정합니다(제안 0.2%p).
  • 게이트별 장치: A·B는 5070에서 탐색해도 되지만 채택한 설정은 운영 장치에서 다시 채점합니다. C는 운영 장치의 holdout으로만 판정합니다. 0.97 임계값이 장치 간 수치 차이에 민감하기 때문입니다. D는 D-CPU와 D-GPU로 나눕니다.
  • '시간 안에 들 때만 채택'(탐지 1920, 2fps)은 운영 장치의 시간 기준입니다. 운영이 CPU면 D-CPU를 통과해야 합니다. 2·4fps로 올리면 시작·끝 창 밖의 1초 미만 일반 자막을 잡을 확률이 2배·4배가 됩니다. 시작·끝 3초는 이미 0.2초 간격이라 달라지지 않습니다.
  • 3단계 GPU 고장 처리: 시작 카나리가 기대 문구와 다르면 GPU를 쓰지 않습니다. CUDA error 719가 나면 워커를 끝내고 남은 프레임만 새 프로세스로 1회 다시 돌린 뒤, 또 실패하면 failed_stage="ocr"로 끝냅니다.
  • CI: 실제 GPU와 유료 호출은 pytest marker gpu·paid로 기본 제외합니다. 실기 결과는 수동 스크립트(--confirm-paid)로만 얻어 벤치마크 보고서에 실측으로 남깁니다.

D시간·메모리

D-CPU(팀 PC): 60초 1건 전체 p50 ≤ 180초 · OCR ≤ 160초 · 프레임 추론 p50 ≤ 1.8초 · 작업자 최대 메모리 ≤ 11GiB(16GB PC의 70%). D-GPU는 운영을 GPU로 정할 때만 씁니다: 전체 p50 ≤ 60초 · OCR ≤ 40초 · 최대 VRAM ≤ 9GiB(12GB의 75%) · sysmem fallback 끔(제안값, 첫 실측 뒤 한 번 조정).
